# M7.6 Performance (A17): result and investigation

Date: 2026-10-14

**Result: not passed.** The largest-contentful-paint target is missed on all four routes. The performance score, layout shift, and interaction targets are met. M7.6 and A17 therefore stay open. Full numbers, machine, browser versions, and throttling are in [performance.md](performance.md) (raw data in `performance.json`), produced by the repeatable procedure `npm run build && npm run perf` (`scripts/perf.mjs`: Lighthouse mobile, three runs per route, medians, route JavaScript transfer, and a long-task trace).

| Route | Performance (target 90) | LCP (target 2.5 s) | CLS (target 0.1) |
| --- | ---: | ---: | ---: |
| Overview | 97 | 2.56 s, misses | 0 |
| Theme | 95 | 2.71 s, misses | 0 |
| Components | 96 | 2.56 s, misses | 0.063 |
| AI Context | 94 | 2.86 s, misses | 0.063 |

Interaction trace: no long task above 50 ms while editing the Theme or filtering the catalog. The script's self-check detects a deliberate 120 ms busy loop, so those zeros are real; an earlier version of the check failed that self-test, which exposed that a first trace had measured nothing, and the trace was fixed before any result was recorded.

## Investigation (evidence, not a changed budget)

- **It is not the page content.** A plain static HTML page scores 100 with LCP about 0.7 s on the same machine and procedure. Statically rendered `/docs/concepts` and `/getting-started` missed the target by the same margin as the interactive routes, so the cost is in the shared JavaScript.
- **Real-browser paint is fast.** In Chromium with a 4× CPU slowdown the Overview paints its largest element at 0.66 s, with a single LCP candidate and no font-swap shift. Lighthouse's simulated slow-4G model (1.6 Mbps, 150 ms round trips) turns about 200 KB of gzipped JavaScript into the extra seconds, and the local `next start` server speaks HTTP/1.1, which that model penalizes for the 20-plus requests.
- **Lighthouse names unused JavaScript** as the main lever (about 1.1 s of modeled LCP before fixes).

## Changes made as a result

- Every page's HTML embedded the whole registry (about 100 KB of JSON) as props for the theme provider. The provider now receives a slim theme system (presets, fonts, tokens, and only the component fields theme validation needs); the Theme editor and appearance selector read it instead of importing the registry. The store module no longer imports the registry.
- The mobile navigation drawer (React Aria, about 50 KB gzipped) loads only when first used or when its trigger is hovered or focused.
- The Overview's 29 live previews load only when they approach the viewport; their cards render on the server.
- Component Detail waits for saved settings before choosing a starting variant (a race the load exposed).
- Unused markdown code was kept out of the agent-file module. First-load JavaScript for the Overview fell from about 300 KB to 212 KB gzipped, and from 180 KB on article pages.

## What remains

About 175 KB of gzipped first-load JavaScript is still shipped on a static page: React and Next (about 126 KB), the validation library (36 KB), and the state library (10 KB). Dropping the validation library from the first load needs the theme runtime and persistence to stop depending on it, which is a larger change than this task. Tried and rejected: inlining CSS gave no gain, and a local HTTP/2 comparison could not be completed. No target was relaxed, and no measurement setting was chosen to make a route pass.

Next steps if this gate is to close: remove runtime schema validation from the first-load path, or accept a recorded exception with the owner's approval. Neither has been done.
