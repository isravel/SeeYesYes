# M7.4 manual test checklist (for a human tester)

Status: **not done.** An agent prepared this checklist. Only a person may run these checks and record results; do not mark any item as passed on someone else's behalf.

Record, for the whole session: tester name, date, operating system and version, browser and version, assistive technology and version (screen reader, and any magnification or voice tools), and the build tested (`git rev-parse --short HEAD`, production build).

## Keyboard (all screens)

For each of the 13 views and the unknown-route page, using only the keyboard:

- [ ] The skip link is the first Tab stop and moves focus to the main content.
- [ ] Tab order follows reading order; nothing is skipped and there are no traps.
- [ ] Focus is always visible and never hidden behind other content.
- [ ] Every control can be operated (Enter, Space, arrows as appropriate).
- [ ] The mobile navigation drawer (narrow window) opens, keeps focus inside, and Escape closes it and returns focus to its button.

## Screen reader: required areas

Test with at least one screen reader and note the pairing (for example VoiceOver with Safari, NVDA with Firefox or Chrome).

- [ ] **Theme forms** (`/system/theme`): every control has a clear name, role, and state; draft, unsaved, warning, and conflict messages are announced; Apply and Discard outcomes are announced.
- [ ] **Dialog** (Component Detail and the Theme preview): the dialog has a name, focus moves in, Tab stays inside, Escape closes it, and focus returns to its trigger.
- [ ] **Dropdown Menu**: the trigger is named, the menu opens with the keyboard, items are announced with their count, Escape returns focus.
- [ ] **Tabs**: tab and panel relationships are announced, arrow keys move between tabs, and the selected state is announced.
- [ ] **Validation details**: selecting a result opens details that are announced and reachable; the demo-result label is announced; copy feedback is announced.
- [ ] Also spot-check: loading, error with Retry, and empty states; the Tokens and Components filters and result counts; AI Context export controls; the documentation search and its result count.

## WCAG criteria review

Use the full [WCAG 2.2 Level A and AA criteria](https://www.w3.org/TR/WCAG22/) to record applicability, result, evidence, and any exception for each criterion. Mark a criterion not applicable only with a reason. The UI checks above are a starting point, not a complete criteria review. Include 2.4.11, 2.5.7, 2.5.8, 3.2.6, 3.3.7, and 3.3.8 when deciding applicability. The project's own contrast calculation covers only the listed pairs and is not an audit.

## Zoom and visual review (M7.5, A14 and A18)

- [ ] Set the browser's actual zoom to 200% in a 1280px-wide window. Visit all 13 views, a component detail page, a documentation article, and the unknown-route page. Check that content stays readable, controls remain reachable, and there is no page-level horizontal overflow. The automated 640px viewport check is only a reflow proxy.
- [ ] Review light and dark component previews with compact, comfortable, and spacious density and sharp, soft, and curvy radius. Check focus visibility, text clipping, overlap, and the layout of controls.
- [ ] Review mobile navigation, code blocks, tables, Theme controls, long content, and standalone, nested, and overlay examples. Record any visual issues and the route and settings that reproduce them.

## Recording results

Add a dated results file under `docs/evidence/M7/` with the session details, each item above marked passed, failed, or not tested, a note for every failure or exception, and links to any issues. Keep M7.4 and the human part of M7.5 open while their checks are failed or untested. If a component passes review, set its `accessibility.status` and `evidence` in the registry only then; until that is done, every component stays "Not reviewed".
