# Evaluation track: E1, E2, and E3 (tooling and fixtures)

Date: 2026-10-14

These three tasks build the evaluation's tooling during M6. They do not run any evaluation: E4 needs an operator, and E5 reports its results.

## E1: task files

`evaluation/tasks/T1.md` to `T8.md` hold the eight fixed tasks from the evaluation plan, each with a developer-style prompt, expected components, probed rules, and a requirements checklist (five to six items each). A test (`tests/evaluation-tasks.test.ts`) checks that every file has every part, that expected components and probed rule IDs are real and match the specified table, that prompts never name SeeYesYes components, exported identifiers, rule IDs, or variants, and that no prompt shares any five-word sequence with a registry example's title, code, or explanation. The check caught one problem: T5's button label matched a registry example title, so the prompt now uses a different label.

## E2: fixture app, reset script, and conditions

`evaluation/fixture-app/` is a minimal Next.js template with one empty page per task (`/t1` to `/t8`). `evaluation/reset.mjs` writes a clean copy to `evaluation/work/fixture-app` before every run (discarding anything a previous run left) from the template plus the shipped component source and its types only. `--verify` installs the copy's own dependencies, type-checks, and production-builds it; that was run and passed.

C0 hides nothing it should not: the test builds a copy and confirms it has no registry data, content, documentation, tests, scripts, `AGENTS.md`, `CLAUDE.md`, `llms` files, or README, that none of the registry's principles, project guidance, rule IDs and text, example titles, or component purposes and guidance appear anywhere in it, that it also never mentions the product name or registry, and that every import resolves inside the copy. Building the test found and fixed real leaks: theme validation lived in the same file as registry rules, so it moved to its own module; and comments in two component-side files mentioned the registry and `/llms.txt`. The copied files match the computed import closure of the components exactly.

`evaluation/context.ts` prepares what a run receives per condition from the shipped exports under the default preset, and never edits them: C0 nothing; C1 the `AGENTS.md` snippet; C2 that plus the task export for the task's expected components; C3 that plus the full export. It reports the bytes of context added (strictly increasing from C0 to C3).

## E3: scoring script

`evaluation/score/` scores only the files a run changed or added compared with a clean copy. Automated checks are keyed by contract rule ID with severity taken from the rule: raw color literals in code and CSS (`token-no-raw-color`), clickable non-interactive elements (`avoid-custom-button`), Button used for navigation and anchors without a real destination (`prefer-semantic-link`), imports outside contract public modules, native elements where a component exists, and non-contract UI libraries (`component-prefer-existing`), removed focus outlines (`wcag-focus-visible`), plus review-flagged custom inline sizing (`minimize-custom-css`) and stacked attribute-less wrappers (`avoid-unnecessary-wrapper`). A type check catches unknown variants and disallowed combinations, `--build` runs the production build, and axe-core runs on given URLs, mapping color contrast findings to `wcag-contrast`. Manual items (requirements, wrapper and custom-CSS review, keyboard checks for T2, T6, and T8) are listed in the output and are not scored automatically.

Tested against the registry: each automatable rule's violation example is flagged under that rule with the rule's severity, its corrected example reports nothing, all 29 recommended examples report nothing (no false positives on correct code), and every violation example is flagged. The CLI was exercised end to end on a fixture page: it reported an error-severity clickable `div`, a Button navigating, raw colors, and review-flagged inline padding, and axe reported a serious `wcag-contrast` finding on a low-contrast sample.

Verification: `npm run check` passed (386 unit tests; 35 new across E1 to E3). `evaluation/README.md` documents the operator workflow.

E4 (round 1) needs an operator and is not started. E5 follows E4.
